Why VS Code Gets Away With HTML Nodes

VS Code (via the Monaco editor) relies on strict architectural constraints to prevent the browser from ever doing expensive layout work:
• Viewport Virtualization: It never renders the whole file in the DOM. It only creates <div> elements for the exact lines currently visible on screen (plus a tiny buffer).

How the Browser "Partitions" HTML Rendering

1. How Garbage Collection Interacts with a <div>

In Electron (Chromium), a <div> does not live solely in JavaScript. It is split across two worlds connected by a unified heap:

• The C++ DOM Object (Blink / Oilpan): When you call document.createElement('div'), Chromium's rendering engine (Blink) allocates a C++ HTMLDivElement on its own garbage-collected heap called Oilpan.
• The JS Wrapper (V8): V8 creates a lightweight JavaScript wrapper object (HTMLDivElement) that points to the C++ object.
• Cross-Component Tracing: V8 and Oilpan trace references together as one unified graph.
	• As long as the <div> is attached to the active document tree, Blink's root keeps the C++ HTMLDivElement alive—which in turn keeps its V8 wrapper
    (and any expando properties or event listeners attached to it) alive.
	• Once you call div.remove() (or clear innerHTML) and drop all JS variables/closures/listeners referencing it, neither V8 nor Oilpan can reach it from a root.
    Both the C++ node and the JS wrapper are swept on the next GC cycle.
	• Detached DOM Trap: If you remove the <div> from the DOM, or collapse a folder and remove its child <div>s,
    while still holding a reference to any single node in that detached subtree (even one child <div>),
    Blink's internal tree pointers (parentNode, firstChild, nextSibling) keep the entire detached tree alive in memory.

2. How Many References / Fields Are Added per <div>?

Assuming every internal slot/field acts as a reference edge in the object graph, creating and attaching a single <div> with text adds roughly 15 to 25 direct object references across
V8 and Blink (not hundreds). Most of the "fields" you see when inspecting a <div> in DevTools are prototype getters/methods shared across all HTMLDivElement instances—they cost
0 bytes and 0 references per instance.

Here is the actual per-instance breakdown:

A. V8 (JavaScript Heap) — ~3 to 5 references

1. The JS Wrapper (HTMLDivElement): A tiny V8 object (~24–32 bytes) containing:
	• Hidden class (Map) pointer (shared)
	• Properties backing store pointer (empty unless you attach custom div.myProp = ...)
	• Elements backing store pointer (empty)
	• Internal Embedder Fields (2 pointers): One pointing to the C++ HTMLDivElement in Oilpan, and one for type/wrapper info.
2. Event Listener Map (if used): If you attach onclick directly to each <div>, V8 allocates a listener wrapper/closure per <div>.
   (Using event delegation on the explorer container reduces this to 0 per <div>.)

B. Blink / Oilpan (C++ Heap) — ~12 to 20 references

An HTMLDivElement inherits from HTMLElement -> Element -> ContainerNode -> Node -> EventTarget. In C++, a flat <div> containing a line of text actually creates two C++ nodes
(HTMLDivElement + a child Text node) plus layout/style structures:

• Tree Pointers (~8 pointers total across the <div> and its Text node):
	• parent_or_shadow_host_ (points to explorer container)
	• first_child_ & last_child_ (on the <div>, pointing to the Text node)
	• previous_ & next_ sibling pointers (linking to adjacent rows)
	• tree_scope_ (points to Document)
• RareData / Attributes (~1–3 pointers):
	• Blink uses a lazy ElementRareData pointer (null by default).
	• Setting className, style, or dataset allocates an ElementData / AttributeCollection and InlineCSSStyleDeclaration (~2–3 pointers).
• String Data (~1–2 pointers):
	• The Text node holds a WTF::String pointer to the underlying character buffer (StringImpl).
• Style & Layout (~3–5 pointers once rendered):
	• ComputedStyle pointer (mostly shared via Blink's style cache)
	• LayoutObject (LayoutNGBlockFlow for the <div> + LayoutText for the string), which hold parent/sibling layout tree pointers and line-box/fragment data.

How are DOM children "stored" behind the scenes. For example the simplest way would assumedly be to allocate a List of child nodes foreach node that contains children.




<
DOM children are not stored in a list or array per parent node; instead, Chromium's Blink engine uses an intrusive doubly-linked list distributed across the nodes themselves.

Rather than allocating a separate List or Vector object on each ContainerNode (which would waste memory on empty containers and require resizing/reallocation on every insertion or removal),
Blink embeds sibling pointers directly inside every Node.

How Blink Stores Tree Relationships

Every C++ Node instance carries 3 tree pointers:
• parent_or_shadow_host_ (points up to the parent ContainerNode)
• previous_ (points to the immediately preceding sibling Node)
• next_ (points to the immediately following sibling Node)

Any node capable of having children (ContainerNode, which HTMLDivElement inherits from) adds just 2 more pointers:
• first_child_ (points to the first child Node)
• last_child_ (points to the last child Node)

```text
[Parent ContainerNode]
  ├── first_child_ ──────────────────────────┐
  └── last_child_ ───────────────────────────│───────────┐
                                             ▼           ▼
  null ◄── [prev] [Child 1] [next] ◄──► [prev] [Child 2] [next] ──► null
                     │                             │
                     └──────────► parent ◄─────────┘
```

Why the DOM Uses Linked Pointers Instead of a List

1. Zero Extra Heap Allocations: Appending or removing a <div> requires 0 heap allocations for container storage—it just rewires 2 to 4 pointers in O(1) time.
2. Low Overhead for Leaf Nodes: A leaf <div> with no children only pays for two nullptr fields (first_child_ and last_child_) instead of an empty array header (data*, size, capacity).
3. Why .children and .childNodes Feel Like Arrays in JS:
	• When you access parent.children or parent.childNodes in JavaScript, Blink lazily creates a lightweight HTMLCollection or NodeList wrapper (stored in NodeRareData).
	• Even then, it does not copy the nodes into an array. Instead, the NodeList caches a single cursor (last_accessed_node, last_accessed_index)
    so sequential loops (for (let i = 0; i < children.length; i++)) step along next_ in O(1) per step, while random indexing (children[500]) walks the linked list from the nearest cached point.

Implications for Your File Explorer
• Sequential Append / Remove is Cheap: Appending 500 <div> rows or clearing container.textContent = '' walks first_child_ → next_ linearly without array shifts.
• Index Lookups are O(n): Calling container.children[index] repeatedly with random indices walks sibling pointers under the hood.
  In a flat file explorer, keeping your own JS array of row metadata (or reusing a fixed pool of <div> elements via a virtual scroller) avoids both DOM pointer chasing and GC churn altogether.

A fixed pool of ~50 DOM elements adds virtually zero Old Generation (Old Space) GC overhead—roughly 2 KB of V8 Old Space memory and microseconds per major GC cycle.

Here is why persistent pooled DOM nodes are nearly free in V8 and Blink's garbage collectors, compared to short-lived or large dynamic trees:

1. How V8 & Oilpan Handle Old Generation Objects
V8 uses a generational collector (Scavenger for New Space / Young Generation, and Mark-Sweep-Compact for Old Space / Old Generation), tightly coupled with Blink's Oilpan C++ heap:
• Young Generation (Scavenge): Runs very frequently (every few megabytes of allocation) and only copies surviving objects.
  Because a fixed pool of <div> elements is allocated once at startup, those wrappers survive two scavenges and immediately promote to Old Space.
  After startup, 0 bytes of DOM wrappers ever enter New Space during scrolling or folder toggling.
• Old Generation (Major GC / Incremental Marking): Runs infrequently and walks live object pointers from roots.
  However, V8 only traces the JS wrapper (HTMLDivElement), not the C++ internals, unless a cross-heap reference exists:
	• No custom JS expandos or closures = minimal tracing: A plain HTMLDivElement wrapper in V8 Old Space is ~32 bytes with zero outgoing JS heap pointers
    (its Map is shared, and its properties/elements pointers point to a singleton empty array).
	• Oilpan's C++ pointers are invisible to V8: Blink's parent_, next_, LayoutObject, and ComputedStyle pointers live on the C++ heap, not V8's Old Space.
    When Oilpan runs incremental marking, walking 50 HTMLDivElement C++ objects takes under 5 microseconds.
	• Write barriers only fire on pointer mutation: Updating div.textContent = "index.js" or div.style.transform = ... mutates C++ fields inside Blink, not V8 heap pointers.
    It does not dirty V8's remembered sets or trigger write barriers.

2. Where Old Generation Overhead Actually Comes From

The real Old Generation GC pauses in a monolithic JS text editor do not come from 50 pooled <div> elements; they come from JS-side allocations:

Source                                                | Old Generation Impact              | Why
=======================================================================================================================================================================================================
50 Pooled <div> Elements                              | Negligible (~2 KB V8 + ~20 KB C++) | Static graph, zero outgoing JS references, never reallocated.
10,000+ Unpooled <div> Elements                       | Noticeable (2–10 ms per Major GC)  | Oilpan must trace 20,000+ C++ nodes (div + Text), layout objects, and wrapper references on every full GC.
File Tree Metadata Objects ({ name, path, children }) | Moderate to High (if large)        | Every JS object/string in a 50,000-file workspace sits in V8 Old Space and must be traced by V8's marker.
Editor Text Buffer / Line Arrays / Undo Stack         | Highest                            | Millions of string slices or line objects in V8 Old Space are the primary driver of Major GC pause times.

3. The 3-Canvas Advantage: Unified Rendering Pipeline

Even though 50 pooled <div>s have essentially zero Old Generation cost, a 3-canvas explorer still offers one clean architectural win for your specific app:
• Zero Layout/Style Recalculation in Blink: Even with pooled <div>s, mutating textContent and transform marks those 50 nodes dirty for Blink's style/layout/paint pipeline before the next frame.
  With 3 canvases, your entire window becomes a pure pixel-blitting surface driven by a single requestAnimationFrame loop with zero Blink style or layout work at all.

If you keep the DOM pool to ~50 rows and avoid attaching per-row closures or custom properties to the <div> wrappers, Old Generation GC overhead is completely non-existent.

In modern V8 (Electron), noticeable main-thread UI stutters (>16ms frame drops) typically begin around 500,000 to 2,000,000 live Old Generation objects with outgoing references,
or roughly 150–300 MB of live pointer-heavy heap.

Even though objects vary wildly in size and depth, V8’s Major GC (Orinoco) has very predictable bottlenecks because of how it splits work across threads.
Understanding the difference between marking and sweeping/compacting makes it much easier to reason about your text editor's ceiling.

1. Why Object Count & Pointer Depth Matter More Than Byte Size

In V8's Mark-Sweep-Compact collector, the time it takes to run a Major GC is not proportional to total megabytes—it is proportional to the number of live objects and pointer edges the marker
has to traverse:
• 1 big ArrayBuffer or Uint32Array of 100 MB = 1 object, 0 outgoing pointers. V8 traces it in nanoseconds. It causes zero GC pause degradation.
• 2,000,000 small JS objects of 48 bytes each (also ~96 MB) = 2,000,000 nodes + ~6,000,000 pointer edges. V8 must dereference every pointer, check its Map (hidden class),
  and push/pop it on the marking deque.

2. Where User-Visible Stutter Actually Happens (The 16.6ms Frame Budget)

Modern V8 does ~90% of Old Generation marking concurrently on background worker threads while your JS runs on the main thread. However, three phases still pause the main thread:
1. Incremental Marking Steps (~1–3ms slices): When allocation rate outpaces background threads, V8 steals small slices of main-thread time between frames.
   Around 500k+ live objects, these slices start eating into your 16.6ms (60fps) or 8.3ms (120fps) frame budget during fast scrolling or typing.
2. Atomic Pause / Finalize Marking (~5–20ms+): Before finishing a Major GC, V8 must pause the main thread to drain remaining marking queues and trace root handles
   (including Blink/Oilpan cross-references). Around 1M–2M+ live JS objects, this final pause crosses the 16ms threshold and causes a visible micro-stutter.
3. Compaction / Evacuation (The Real Frame-Killer): When Old Space becomes fragmented (lots of deleted objects mixed with surviving ones), V8 copies surviving objects to
   contiguous pages and updates every pointer in the heap that points to them. High pointer density + fragmented Old Space is what causes rare 30–100ms+ freeze spikes.

3. Practical Thresholds for a Text Editor

To keep a text editor feeling instantaneous (zero dropped frames while typing or scrolling):


Live Old-Gen Object Count | User Experience in Electron / V8                                                  | Typical Editor Equivalent
========================================================================================================================================================================================================================================
< 100,000 objects         | Completely invisible (< 1–2ms atomic pauses).                                     | Small/medium project, flat line arrays, pooled DOM.
250,000 – 500,000 objects | Smooth, occasional minor frame dip only during heavy allocation spikes.           | Large repo (~50k files) stored as nested JS objects, or a 200k-line file with per-token objects.
1,000,000+ objects        | Noticeable micro-stutters (15–40ms) during Major GC atomic pauses and compaction. | Deeply nested ASTs, massive undo histories storing full document snapshots, or unvirtualized file trees of node_modules.

4. Three Rules of Thumb to Stay Well Below the Ceiling

Since your app is a single monolithic vanilla JS module—which already avoids framework virtual-DOM object churn—you have full control over your object graph:
1. Flatten Graphs Into Parallel TypedArrays / Flat Arrays: Instead of 100,000 tree node objects ({ id, parent, children[], name, depth }), store tree metadata in parallel flat arrays
   (depths = new Uint8Array(N), parentIndices = new Int32Array(N), names = []). V8 skips tracing raw TypedArray buffers completely.
2. Avoid Mutating Old-Gen Pointers: Reassigning properties on long-lived objects (oldNode.next = newNode) triggers V8 write barriers to record old-to-new pointers.
   Replacing whole slices or using index integers (nextIndex = 42) instead of object references eliminates write barrier overhead entirely.
3. Strings Count as Objects: Every sliced or concatenated string in V8 (ConsString, SlicedString, SeqOneByteString)
   is a separate Old Generation heap object (~24–40 bytes header + payload).
   Keeping raw text in a piece table or gap buffer backed by Uint8Array/Uint16Array (or chunked strings) prevents millions of tiny line/token strings from flooding Old Space.
